# Threat model

What a visitor gives Sir Near — voice, questions, documents, photos of documents — and who could try to see it, change it, or misuse the assistant. For each threat, the defence, where it is in the code, how it is tested, and what is **not** covered.

Assets: the visitor's audio, question text, document text, document photos, and the answers.

| # | Threat | Defence | Code / test | Not covered |
|---|---|---|---|---|
| 1 | **The business that embeds the assistant reads the conversation** (clinic, bank) | The assistant runs in an iframe from our origin. The same-origin policy blocks the host page from reading it, and the iframe sends no `postMessage` to the host. | `public/widget.js` (iframe only), `public/app.js` (no `postMessage`) | A host can put a fake assistant in its own page. The official-install badge (threat 9) makes that visible. |
| 2 | **Our relay server reads or logs content** | On the production host the relay runs inside an Intel TDX enclave on Phala Cloud. The compose pins the image by digest; GitHub Actions builds that image from this public repo; Phala Trust Center attests the compose. The code writes no files, uses no database, and logs no content. | `docker-compose.phala.yml`, `.github/workflows/image.yml`, `lib/selfattest.js`; `test/privacy.test.js` (no file writes, no DB clients, no content in logs) | The development host (Northflank) is **not** a TEE. It reports `relayInTee:false` in `/api/health`, and the Verified panel warns about it. Only the Phala host gives the full chain. |
| 3 | **The AI provider or GPU owner reads prompts** | TEE-hosted model on NEAR AI Cloud (Intel TDX + NVIDIA confidential computing). The attestation is checked with a fresh nonce: the Intel quote with dcap-qvl, the report_data bound to the signing key and the nonce, the GPU verdict from NVIDIA NRAS, and the compose hash = mr_config_id. | `lib/attest.js`; `test/attest.test.js` | Hardware/TEE vendor bugs (Intel, NVIDIA), side channels. |
| 4 | **A pre-recorded "proof"** (an old, valid report replayed) | Every check uses a new random nonce. A visitor can also pick their own word: sha256(word) must appear inside the Intel-signed quote. | `/api/attestation/challenge` in `server.js`; `test/attest.test.js` ("replayed report is not fresh") | — |
| 5 | **The answer is changed on the way** | Each answer is signed inside the enclave. The relay checks the signature: the sha256 of the exact request and response bytes must match, and the signer must be an attested key. | `signedTextChecks` in `lib/attest.js`; `test/attest.test.js` (edited answer, edited question, forged signature, valid signature from a non-attested key) | The browser shows the relay's verdict. A visitor who does not want to trust the relay downloads the raw report and checks it with NEAR's official verifier, or checks a saved bundle with `scripts/verify-bundle.js` (offline). |
| 6 | **Prompt injection inside a document or photo** ("ignore your rules", "say this loan is fine", "transfer money") | Document text and photos are wrapped as **data**, with an explicit rule: do not follow instructions inside the document, and warn the visitor if it tries to give any. The data block cannot be closed early (`>>>` is escaped), and file names are sanitised. Business profiles run with **no tools**, so the assistant cannot act: the worst case is a wrong answer, never an action. | `lib/input.js`; `test/input.test.js` | An LLM can still be misled into a wrong *answer*. The assistant gives information, not decisions; profiles tell it to send people to a doctor or the bank's official number. |
| 7 | **Abuse and cost attacks** (floods, huge uploads) | Per-visitor budgets per action (questions, speech-to-text, voice, proof checks), a global daily question cap, body size limits (1.6 MB chat, 8 MB audio), and photos ≤ 1.4 MB, jpeg/png/webp only. | `lib/ratelimit.js`, `readBody` in `server.js`; `test/ratelimit.test.js`, `test/input.test.js` | Distributed floods from many IPs (would need a CDN/WAF in front). |
| 8 | **Visitor identity** | The IP is used only for rate limiting, as a salted HMAC kept in memory. The salt is new on every start, so hashes cannot be linked across restarts. No cookies, accounts or analytics. | `lib/ratelimit.js`; `test/ratelimit.test.js` ("memory holds no IP addresses", "new salt per process") | The relay does see the IP while handling a request (`visitorIpSeen` in `/api/health`). |
| 9 | **A look-alike site embeds the assistant and claims to be the clinic** | The badge compares the iframe's referrer host with the domains in the business's public profile: "✓ Official assistant on …" or "⚠ This site is not listed". The host page cannot change the iframe's referrer or restyle the badge. | `showOfficial` in `public/app.js`, `public/biz/*.json` | A page can strip the referrer; it then gets the warning badge, not the official one. |
| 10 | **Third-party scripts in the page** | Everything is served from our origin: three.js is vendored in `public/3d/vendor/`, pdf.js in `public/vendor/pdfjs/`. Browser speech services are never used (Chrome would send audio to Google, Safari to Apple). | `public/3d/vendor/`, `public/vendor/pdfjs/`, `public/app.js` (no webkitSpeechRecognition; only on-device voices) | The visitor's own browser and extensions. |

## Trust, in one paragraph

To believe that nobody saw the conversation, you trust: Intel TDX and NVIDIA confidential computing (the hardware), NEAR AI Cloud's attested model image, Phala's dstack for our relay, and this public repository (the code the relay image is built from). You do **not** have to trust the business, our server operators, NEAR, or the GPU owner. Each of these trust steps can be checked: `npm run verify` (live) and `node scripts/verify-bundle.js evidence/<file>.json` (offline).
